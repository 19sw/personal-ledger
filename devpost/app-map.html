记账应用地图

一张随身带走的小地图：这个应用由哪几块组成、一笔账从哪里进来、以后想改东西该从哪里下手。

这个应用是什么

一个在 iPhone Safari 里使用的个人记账网页。账本是你自己 Google 账号里的一张 Google 表格，程序运行在 Google Apps Script 上，只有你本人能打开。它的核心特点是：实体店付款（Apple Pay）和线上付款（Gmail 收据）汇入同一本账，同时区分不同兼职的收入；读不到金额的账目不会丢，而是标成“待补全”。

主要的几块
  • apps/main/ui/：你在手机上看到的页面（HTML、样式和页面脚本）。
  • apps/main/web.js：页面能调用的服务器函数，名字都以 api_ 开头。
  • apps/main/core/：真正的记账规则——保存账目、月报、预算、小助手、收据识别。这些是纯函数，所以能在本机用 Node 测试。
  • apps/main/store.js：把 Google 表格包装成“列出／新增／修改”的接口。
  • apps/main/jobs.js：定时任务——整理 Apple Pay 收件箱、读 Gmail 收据、每日清理。
  • apps/inbox/：独立的“记账-收件口”，接收 iPhone 快捷指令送来的 Apple Pay 交易。
  • tests/：自动测试，用假的表格和假的 Gmail 跑真实代码。

一笔账是怎么进到账本的

参考路线：跟着“记一笔”走三站

参考路线，尚未实际带你走过 打开项目后，用编辑器的搜索功能找下面加粗的名字即可定位（行号会随修改变化，名字不会）。

1

你点“保存”的地方

apps/main/ui/app.js.html，搜索 function saveForm。它先检查有没有填金额（防止空记录），把按钮缩成圆形做动画，然后通过 api('api_saveEntry', input) 把这笔账发给服务器。

看一眼关键代码 
if (!state.draft.id && !amountIsPositive(state.draft.amount)) { showHint('先填金额'); return; }
var input = collectForm();
...
Promise.all([api('api_saveEntry', input), ...]).then(function (res) { ... });
2

服务器的大门

apps/main/web.js，搜索 function api_saveEntry。它先拿到“锁”（同一时间只让一个操作改账本，防止和定时任务撞车），再把工作交给 svcSaveEntry。

3

真正的记账规则

apps/main/core/service.js，搜索 function svcSaveEntry。这里检查输入是否合法、新建或修改账目、写进表格（repo.insert('entries', ...)），然后记一次打卡（svcOnEntryCreated_）并检查是否和 Apple Pay 等其他入口的账目疑似重复。保存完成后，页面刷新，你就在账目页和月报里看到它了。

想改东西，从这里开始

  • 页面上的文字、按钮、布局：apps/main/ui/index.html 和 apps/main/ui/app.js.html。
  • 颜色和样式：apps/main/ui/style.html。
  • 默认类别清单：apps/main/core/service.js 搜索 svcEnsureDefaults。改完要重跑 setupLedger 才会补进已有账本。
  • 小猫助手说什么、什么时候提醒：apps/main/core/assistant.js。
  • 月报怎么算：apps/main/core/report.js；预算在 apps/main/core/budget.js。
  • 某个平台的收据怎么识别：apps/main/core/platforms/（doordash.js、ubereats.js、uber.js）；共用流程在 apps/main/core/receipt_pipeline.js。
  • 改完之后：先跑测试；涉及新的 api_ 函数时，tests/ui.test.js 会要求把它加进评审过的名单，这是故意设的安全关卡。

一个可以带到下个项目的做法

先用真实数据做一次只读试运行，再开启自动化。

Gmail 收据没有直接开启自动入账，而是先做了只读的 G1 试运行（apps/main/jobs.js 的 dryRunReceipts，规则见 devpost/spec.md 第 6.8 节）。它不写账本，只报告“读到了什么”。结果推翻了好几个原来的假设：DoorDash 收据里读不到订单号、Uber 邮件其实都是打车、熊猫外卖根本没有邮件。于是方案在开启轮询之前就改了：去掉熊猫外卖、Uber 记成“交通”、DoorDash 改用“同一家餐厅＋6 小时内”判断重复，这些情况都写成了合成样本测试（tests/receipts-rules.test.js、tests/receipts-pipeline.test.js）。

换到别的项目也一样：只要要接一个不熟悉的外部数据来源，先做一个“只看不改”的试运行，拿真实结果对照计划，再决定怎么写规则。这样坏消息来得早，改起来也便宜。

怎么再跑起来

cd Build-With-AI-Basics
npm install
npm test          # 运行全部自动测试
npm run preview   # 在本机浏览器预览页面（使用假数据）

上线到 Google：在 apps/main 目录里运行 npx clasp push --force，再在 Apps Script 里更新部署。完整步骤见 docs/setup-guide.md。
