# 个人记账应用：第一版技术方案（草稿）

> 本文件记录已批准的技术方案和 2026-10-22 的邮件规则更新。任务单 12 的代码尚在本地实现与评审；任何推送、重新运行初始化或发布都要按计划另行征得你的同意。
>
> 来源标注方式：`[S1]` 等编号对应第 13 节的官方文档链接，访问日期为 2026-10-12（S29 及 S11 的计费门槛部分为 2026-10-13）。标 **【未核实】** 的内容没有找到官方依据，需要在验证实验中确认。

## 0. 一页看懂（写给初学者的白话版）

**一句话：** 把整个应用放在你自己的 Google 账号里——账本是一张 Google 表格，程序是 Google 提供的免费小程序（叫 Apps Script，“谷歌脚本”），你用 iPhone 浏览器打开一个网址就能记账、看月报。

**为什么这样选：**

1. **不花钱，而且按设计无法扣费。** 整个方案不绑定信用卡，也不开通 Google Cloud 结算账户。谷歌脚本用超了每日额度，会**报错暂停到第二天** [S1]。**但要如实告诉你：** Google 已宣布，2026 年晚些时候（提前至少 90 天通知）Gmail 接口超过“每日计费门槛”（每个项目每天 8,000 万单位）的用量将收费 [S11][S29]。目前邮件读取量仍是估算；上线前用 G1 实测后更新估算，并再次核对 Google 计费公告。并且只要从不绑定结算账户，就没有可扣款的地方（这一点属于推断，见第 1.1 节）。
2. **只有你能看。** 打开记账网页时需要登录你的 Google 账号，网页设置为“只有我自己能访问” [S3]。
3. **只读处理邮件账单。** 程序内置识别 DoorDash、Uber Eats 和 Uber 打车；其他像收据的邮件只放入待查看，不会自动入账。谷歌脚本直接在 Google 内部读取，不用把“邮箱钥匙”（授权令牌）交给任何外部服务保存。权限申请为“只读”，程序不能发信、不能删信 [S10]。
4. **东西少，好维护。** 不需要服务器、不需要数据库软件，正式运行时没有第三方程序包。账本就是一张你能直接打开查看的表格（学会计的你也可以随时核对）。

**两条自动记账路线：**

- **实体店 Apple Pay：** iPhone 快捷指令在你刷卡后自动运行，把“金额、商家、时间”发送到一个专用的“收件口”（单独的小程序，设计上只能往一张“收件箱表格”里写新行，碰不到你的账本和邮箱；“只能碰这一张表格”的权限设置需在切片 3 实测，若做不到由你决定是否接受更大的权限，见第 11 节 D6）。主程序再把它整理进账本。
- **Gmail 邮件账单：** 主程序每 5 分钟查看名单商家和其他像收据的邮件。DoorDash、Uber Eats 和 Uber 打车按规则自动记账；名单外邮件只进入“待查看邮件”，不会自动入账。用户可把商家加入名单并选择类别。实际时效和总额识别仍需 G1/G2 验证。

**预算与小助手（2026-10-13 新增，见第 7A 节）：** 在设置页设每月总预算（可选给部分类别单独设），每月自动沿用，修改只影响当月及以后。每个页面左上角有小助手图标，有新提醒时显示红点，点开是聊天窗口和 5 个问题按钮。小助手只按固定规则计算，**不调用外部 AI、账目不离开 Google、不能打字**。程序结构为以后增加按钮或升级为 AI 留了接口，但接入 AI 需要你另行批准。这部分不需要任何新的服务或权限。

**目前还不确定、必须靠实验确认的三件事：**

1. iPhone 刷卡后，快捷指令能否稳定取得金额和商家；真实刷卡已验证成功，仍需后续确认日期格式等边界。
2. DoorDash、Uber Eats 和 Uber 打车邮件的实付总额、商家和订单标识规则能否稳定识别；Uber 打车总额标签仍待真实邮件验证。名单外邮件进入待查看，不会自动入账。
3. 谷歌脚本网页在你的 iPhone Safari 上用起来是否顺手（例如登录多个 Google 账号时的已知问题）。

第 5.4 节和第 6.8 节给出了两个具体实验，**第一个实验（看快捷指令能拿到什么）不需要注册任何服务，下一次正常在实体店付款时就能做**。

**需要你决定的主要事项（详见第 11 节）：** 选哪个方案；用哪个 Google 账号；是否同意建立两张表格和两个谷歌脚本项目；是否同意 Gmail 只读授权；是否同意把“收件口”部署成不需要登录的网址（靠一串密码保护）；是否允许安装开发工具。

**按目前公开的规则，没有发现在免费条件下做不到的需求。** 但上面三件事没验证之前，不能宣称两条自动路线可行；另外，Gmail 接口的计费细则尚未公布，上线前要再次核对（风险 R13）。

## 1. 方案选择

### 1.1 推荐方案 A：Google 表格 + 谷歌脚本（Apps Script）

```
iPhone Safari ──(Google 登录)──> [主项目 M：网页 + 定时任务]  ──读写──> 表格「账本 Ledger」
                                        │  每 5 分钟
                                        ├──(Gmail 只读)──> 内置平台邮件与名单外收据候选
                                        └──(只读)────────> 表格「收件箱 Inbox」
iPhone 快捷指令（刷卡触发）──(HTTPS POST + 口令)──> [收件项目 I：只收不读] ──追加行──> 表格「收件箱 Inbox」
```

| 组成部分 | 内容 | 能访问什么 |
| --- | --- | --- |
| 表格「账本」 | 所有账目、类别、来源、去重记录、状态 | — |
| 主项目 M（绑定在「账本」上的谷歌脚本） | 记账网页、月报计算、Gmail 定时读取、整理收件箱、30 天清理 | Gmail 只读；表格读写；管理自己的定时器 |
| 表格「收件箱」 | 快捷指令发来的原始交易（每笔一行） | — |
| 收件项目 I（绑定在「收件箱」上的谷歌脚本） | 只有一个“接收”入口，检查口令后追加一行 | 目标：只能写它所在的这张「收件箱」表格（`spreadsheets.currentonly`，需在切片 3 实测；见 6.1 与 D6） |

**为什么拆成两个项目：** 谷歌脚本网页的访问权限（“只有我”或“任何人”）写在项目的配置文件里，是整个项目共用的 [S3]。记账网页必须是“只有我”；而快捷指令发请求时无法带上你的 Google 登录状态，所以收件口必须是“任何人、无需登录”（`ANYONE_ANONYMOUS`）[S3]。更关键的是：一个“任何人可访问”的部署会对外公开该项目的**全部入口**，也就是 `doGet` 和 `doPost` 都会公开，并且以你的身份（`USER_DEPLOYING`）运行 [S2][S3]。如果放在同一个项目，任何人打开网址都会以你的身份运行记账网页，看到全部账目。拆开后，公开的那个项目代码最少、权限最小：目标是碰不到账本、也碰不到 Gmail。

**主要免费限制（个人 Gmail 账号）及超限后果：**

| 限制 | 数值 | 本应用预计用量 | 来源 |
| --- | --- | --- | --- |
| 定时任务每日总运行时间 | 90 分钟/天 | 每 5 分钟一次 = 288 次/天；每次预计 1–5 秒，约 5–25 分钟/天 **【单次耗时未实测】** | [S1] |
| 单次运行时长 | 6 分钟 | 远低于 | [S1] |
| 邮件读取次数（`GmailApp` 等内置邮件服务的配额；本方案代码不使用 `GmailApp`，列出仅供参考） | 20,000 次/天 | 不适用 | [S1] |
| Gmail 接口配额（本方案实际使用的 Gmail API） | 每用户每分钟 6,000 单位；列表 5 单位/次，读取一封 20 单位/次 | 远低于 | [S11] |
| **Gmail 接口每日计费门槛** | 每个项目每天 8,000 万单位；门槛以下“不产生额外费用、不会向你的 Google Cloud 账户收费”；完整计费细则将于 2026 年晚些时候公布，生效前至少提前 90 天通知 | 使用一次合并列表搜索并限制每轮读取量；名单外收据候选会增加读取量，实际数量待 G1 测量后更新（明细见 6.4） | [S11][S29] |
| 定时器数量 | 每个项目每用户 20 个 | 2 个（5 分钟检查、每日清理） | [S1] |
| 同时运行数 | 30 个/用户 | 远低于 | [S1] |
| 脚本属性（存口令等） | 每值 9 KB，总 500 KB | 几个短字符串 | [S1][S16] |
| 表格容量 | 最多 2,000 万个单元格 | 每年约 1,000 笔 × 25 列 = 2.5 万个单元格 | [S18] |
| 定时器触发时间 | 文档说明时间“可能略有随机”，未给出分钟级定时器的误差范围 | 预计数分钟内 **【误差未核实】** | [S4] |

**超限会怎样：** 超过 Apps Script 配额时，脚本抛出错误，例如“Service using too much computer time for one day”，相关功能停止，直到配额在 24 小时后重置 [S1]。Apps Script 配额页没有超额计费说明。定时任务失败时，Google 会发邮件通知脚本所有者 [S4]；应用也会在设置页和首页显示提醒（见第 8 节）。

**Gmail 接口的计费公告（必须知道）：** Gmail API 配额页写明了“每日计费门槛”（见上表）[S11]。Google Workspace 开发者页面（2026-09-03 更新）也写明：2026 年晚些时候、提前 90 天通知后，“超过标准每日门槛的 API 用量将在你的 Google Cloud 账单上产生费用”，申请提高配额也将要求开启结算 [S29]。本方案的应对：

1. **用量极低：** 约为门槛的 0.003%（计算见上表和 6.4）。即使程序出错、每轮都把 3 天窗口内的全部邮件（假设 150 封、3 页）重新读一遍：按正常的每 5 分钟一轮，约 87 万单位/天（约 1.1%，见 6.4）；即使连定时器也错设为每分钟一轮，1,440 × (3 × 5 + 150 × 20) ≈ 434 万单位/天，约为门槛的 5.4%。
2. **永不绑定结算账户：** 不给 Apps Script 自动创建的默认 Cloud 项目绑定结算账户，**也不把项目切换为“标准 Cloud 项目”**（切换后可以单独开启结算，风险变大）。不申请提高配额。
3. **“没有结算账户就无法扣费”是推断：** 依据是计费描述针对“你的 Google Cloud 账单”，而本方案没有任何结算账户。Apps Script 默认项目在这套计费规则中如何处理，官方尚未公布。**【推断，未核实】**
4. **上线前再次核对：** 每次部署前查看 [S11][S29] 是否发布了新的计费细则；如果规则变为“不绑定结算账户也可能产生费用”，就先暂停 Gmail 路线，再与你讨论（第 11 节第 12 项、风险 R13）。

> 说明：Apps Script 官方页面没有出现“免费”这两个字。“Apps Script 本身不收费”的依据是：配额页只说明超额会报错，没有超额计费；本方案不建立任何结算账户。**【推断，未找到明确的官方“免费”声明】**

**其他已知限制：**

- 网页在 Google 的 iframe 沙箱中运行，链接需要设置为 `_top` 或 `_blank` [S15]。网址很长（`script.google.com/macros/s/…/exec`），建议加到 iPhone 主屏幕。
- 同一个 Safari 里同时登录多个 Google 账号时，谷歌脚本网页可能打不开。这是社区常见问题，**【未核实】**，在第 9 节切片 0b 中实测。
- 谷歌脚本没有官方的自动化界面测试框架，界面检查以手机上的手动检查清单为主（见第 7.3 节）。

### 1.2 备选方案 B：Supabase（数据库 + 登录）+ GitHub Pages（网页）+ 谷歌脚本（只负责读 Gmail）

```
iPhone Safari ──> GitHub Pages 静态网页 ──(Supabase 登录 + 行级权限)──> Supabase Postgres
iPhone 快捷指令 ──(HTTPS + 口令)──> Supabase Edge Function ──> Supabase Postgres
谷歌脚本（每 5 分钟读 Gmail）──(HTTPS + 口令)──> Supabase Edge Function
```

| 限制 | 数值 | 来源 |
| --- | --- | --- |
| Supabase 免费版数据库 | 500 MB；共享 CPU、500 MB 内存；流出流量 5 GB | [S24] |
| Supabase Edge Function 调用 | 500,000 次/月 | [S24] |
| **闲置暂停** | **免费项目闲置 1 周后会暂停**；最多 2 个活跃项目 | [S24] |
| 是否会扣费 | 免费版“不会被收费”；“消费上限”只用于 Pro 付费版 | [S26] |
| GitHub Pages | 仅公开仓库可用（免费账号）；站点 ≤ 1 GB；带宽软上限 100 GB/月；官方说明**不应用于发送密码等敏感交互** | [S27] |

**为什么不推荐 B 作为首选：**

1. **会暂停：** 闲置 1 周会暂停 [S24]。如果你一周没打开应用，暂停后快捷指令和 Gmail 写入可能失败，需要手动恢复。“自动写入算不算活跃”**【未核实】**。
2. **组件多：** 涉及三个服务、两种语言环境，对初学者维护负担更大。
3. **Gmail 仍要靠谷歌脚本：** 如果改为在 Supabase 里直接调用 Gmail，就需要自建 Google Cloud OAuth 客户端。处于 “Testing” 状态的客户端，刷新令牌 7 天就会过期 [S14]，Gmail 读取每周都会断。改为 “Production” 状态则会显示“未验证应用”。Google 还写明：在服务器上保存或传输受限权限数据需要安全评估 [S10]。所以 B 里读 Gmail 的部分仍由谷歌脚本完成，只把提取出的金额等字段发给 Supabase。这同时需要 Supabase 和谷歌脚本，复杂度最高。
4. **GitHub Pages 官方不建议用于传输密码 [S27]：** 登录方式需改为“邮件魔法链接”，回避在 Pages 页面上输入密码。

B 的优点：真正的数据库，有事务和行级权限（RLS）[S28]；界面不受谷歌 iframe 限制，可以做成更像 App 的网页。**如果切片 0b 发现谷歌脚本网页在你的 iPhone 上体验很差，就改用 B。**

## 2. 登录与“只有你能读写”

### 方案 A

| 层面 | 做法 |
| --- | --- |
| 登录方式 | 使用你的 Google 账号登录（Safari 中登录 Google 即可）。强烈建议这个 Google 账号开启两步验证。 |
| 记账网页 | 主项目 M 的网页设置为 `access: MYSELF`（只有部署者本人能运行），`executeAs: USER_DEPLOYING`（以你的身份运行）[S3]。其他人打开网址会被 Google 拒绝，代码不会执行。 |
| 账本表格 | 保存在你的 Google Drive 中，不共享给任何人。 |
| 收件口（项目 I） | `access: ANYONE_ANONYMOUS` + `executeAs: USER_DEPLOYING` [S3]。任何人都能**调用**这个网址，但：(1) 必须带正确口令，否则什么也不写；(2) 目标是项目只能写「收件箱」表格（权限 `spreadsheets.currentonly`），读不到账本和 Gmail（需切片 3 实测，见 D6）；(3) 收件口不返回任何账目数据。剩余风险见第 5.3 节。 |
| 收件口口令 | 一串随机长字符串（例如在脚本编辑器里运行两次 `Utilities.getUuid()` 拼接）。保存在项目 I 的“脚本属性”里 [S16]，同时填在你的快捷指令里。**绝不写进代码或仓库。** 怀疑泄露时：换新口令，并新建一个部署（网址也随之更换）。 |
| 为什么口令放在请求正文而不是请求头 | 谷歌脚本 `doPost(e)` 的参数只包含查询字符串、参数和正文，不包含请求头 [S2]，所以只能把口令放在 JSON 正文里。不要放在网址里，以免出现在浏览记录或日志中。 |

### 方案 B（备选）

Supabase Auth 邮件魔法链接登录。在 `entries` 等所有表上开启行级安全（RLS）：只允许 `user_id = auth.uid()` 的行被读写 [S28]。只允许你的邮箱注册（关闭公开注册）。服务端密钥只放在 Supabase 的环境变量里。

## 3. 主要技术决定一览

| 决定 | 选择 | 理由 |
| --- | --- | --- |
| 运行平台 | Google Apps Script，V8 运行时 [S3 manifest] | 免费、无结算账户、能直接读 Gmail |
| 数据存储 | Google 表格（每类数据一个工作表） | 单人、数据量小；可直接查看核对 |
| 金额存储 | **整数美分**（如 12.34 美元存为 1234） | 避免小数计算误差 |
| 时间存储 | UTC 的 ISO 8601 字符串 + 派生字段 `month_ny`（费城月份，格式 `YYYY-MM`） | 月份归属不受手机时区影响 |
| 项目时区 | 两个项目的配置文件都设为 `"timeZone": "America/New_York"` [S3 manifest] | 定时器和日期格式化都按费城时间 |
| Gmail 读取方式 | 高级 Gmail 服务（即 Gmail API）+ 显式只读权限 `gmail.readonly`；代码中不使用 `GmailApp` | `GmailApp.search` 文档列出的权限是 `https://mail.google.com/`（可读写、可永久删除邮件），另注明“或相关 REST API 的适当权限”。它能否只凭只读权限运行，文档没有写清 **【未核实】** [S7][S10]。Gmail API 则可以明确只申请只读权限 [S8][S10] |
| 读取频率 | 每 5 分钟（允许值为 1、5、10、15、30 分钟 [S5]） | 1 分钟一次会用掉大部分每日 90 分钟额度；5 分钟可满足 15 分钟目标 |
| 并发保护 | `LockService.getScriptLock()` [S17] | 防止定时任务和网页同时写账本，造成重复记录 |
| 图表 | 手写 HTML/CSS 横向柱状图 | 不引入图表库 |
| 运行时第三方包 | **无** | 最小依赖 |
| 小助手 | 纯规则计算；“汇总快照 → 技能 → 消息”三层结构（7A.4） | 零费用、数据不外传；以后加按钮或接入 AI 只需新增技能或回答者 |

## 4. 数据模型（「账本」表格中的工作表）

### 4.1 `entries`（账目）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | 文本 | `Utilities.getUuid()` 生成 |
| `type` | `expense` / `income` | PRD 第 2 节“类型” |
| `amount_cents` | 整数或空 | 空 = 金额未知。支出与收入均存正数；**退款存负数**。手动录入时必须 > 0（PRD 第 4 节） |
| `occurred_at` | UTC ISO 字符串 | 交易发生时间 |
| `month_ny` | `YYYY-MM` | 由 `occurred_at` 按 America/New_York 计算；每次修改时间时重新计算 |
| `category_id` | 文本 | 指向 `categories` |
| `income_source_id` | 文本或空 | 仅收入；空 = “未指定来源” |
| `merchant` | 文本 | 商家／说明。内置邮件自动记录显示 `DoorDash`、`Uber Eats` 或 `Uber`；名单商家显示用户设定名称 |
| `note` | 文本 | 备注 |
| `channel` | `manual` / `apple_pay` / `gmail_receipt` | 创建后不可修改（PRD 第 2、4 节） |
| `platform` | 空或 `doordash` / `ubereats` / `uber` / `sender` | 仅 `gmail_receipt` 使用；界面显示对应商家名称 |
| `is_refund` | 布尔 | 退款标记 |
| `refund_of` | 文本或空 | 原交易 `id` |
| `flag_dup` | 布尔 | 待核对重复 |
| `dup_group` | 文本或空 | 同一组疑似重复的账目共享一个组号 |
| `flag_amount_review` | 布尔 | 待核对金额（小费等修订） |
| `source_key` | 文本或空 | 来源凭据，如 `gmail:msg:<邮件编号>`、`applepay:evt:<触发编号>` |
| `order_ref` | 文本或空 | 平台订单标识（如能提取；与 `platform` 一起使用） |
| `restaurant_key` | 文本或空 | DoorDash 主题中的餐厅名经归一化后计算的不可逆哈希；不保存餐厅原名，仅用于 D7 |
| `created_at` / `updated_at` | UTC ISO | |
| `deleted_at` | UTC ISO 或空 | 软删除时间 |

**状态是计算出来的，不单独保存。** 显示优先级：

1. `amount_cents` 为空 → **待补全**
2. 否则 `flag_amount_review` → **待核对金额**
3. 否则 `flag_dup` → **待核对重复**
4. 否则 → **正常**

用独立标记而不是一个“状态”字段，是因为一笔账可能同时“缺金额”和“疑似重复”。补填金额后，“待补全”自动消失（PRD 第 4 节）。

### 4.2 `processed_sources`（去重凭据，永不清理）

| 列 | 说明 |
| --- | --- |
| `source_key`（唯一） | `gmail:msg:<id>`；`applepay:evt:<event_id>`；`order:<platform>:<order_ref>:receipt` |
| `entry_id` | 生成的账目（可为空，例如“已忽略的促销邮件”） |
| `outcome` | `created` / `ignored_not_receipt` / `ignored_platform_disabled` / `uncertain` / `revision_flagged` / `duplicate_noop` / `refund_created` |
| `processed_at` | 时间 |

**为什么单独建表：** 一笔自动记录被删除并在 30 天后彻底清除后，它的凭据仍留在这里，同一封邮件或同一次触发再被处理时，会因为凭据已存在而直接跳过。这满足 PRD“被删除的自动记录不会重新出现”。这张表不保存金额以外的邮件内容。

### 4.3 其他工作表

| 工作表 | 列 | 说明 |
| --- | --- | --- |
| `categories` | `id, type, name, sort, archived` | 预置 PRD 默认清单。删除一个已被使用的类别时改为“归档”（选择列表中隐藏，历史账目和月报不变） |
| `income_sources` | `id, name, archived` | 兼职来源。新增时去除首尾空格；与已有名称相同（不区分大小写）时，直接选用已有来源，防止统计被拆散 |
| `dup_dismissed` | `entry_a, entry_b` | 你选择“两笔都保留”后记录在此，之后不再把这两笔标为重复 |
| `month_meta` | `month, last_changed_at` | 每次账目新增、修改、删除、恢复时，同时更新受影响的月份（包括改日期前后的两个月份），用于显示“最后更新于…” |
| `budgets`、`assistant_messages`、`assistant_state`、`settings` | 见 7A.1 | 预算历史、小助手消息与状态、可调阈值 |
| `channel_status` | `channel, last_run_at, last_success_at, last_entry_at, last_error_at, last_error_code, last_error_text` | PRD 6.4 状态展示。`last_error_text` 只写错误类型，不写邮件内容 |
| `gmail_pending` | `message_id, platforms, received_at, reason, sender_domain, amount_cents, reviewed_at, created_at` | 待查看邮件；只保存发件网域和识别金额，不保存邮件原文 |
| `mail_senders` | `domain, display_name, category_id, mode, created_at` | 用户管理的商家；`mode` 为 `auto` 或 `muted`，不含内置平台 |

「收件箱」表格（项目 I）的 `inbox` 工作表：`row_type`（`txn` 交易 / `rate_limited` 限流标记）、`received_at, event_id, amount_text, merchant_text, occurred_at_text, shortcut_version, rejected_count`。不保存口令。

**收件箱原始行的保留期：** 主项目整理完一行后，凭据会写进账本的 `processed_sources`，原始行就不再需要。为了在出问题时能够追查，原始行保留 30 天，由项目 M 的每日清理任务一并删除 `received_at` 早于 30 天前的行（项目 M 持有 `spreadsheets` 权限，见 6.1）。**如果项目 M 改用窄权限**（只能读收件箱，见 6.1），就改由项目 I 清理：每次成功写入后顺带删除 30 天前的行（每次最多删 50 行，不需要额外的定时器或权限）。窄权限下，项目 I 读不到账本，因此无法确认某一行是否已被项目 M 整理过。**接受的风险：** 一行在 30 天内都没被整理（项目 M 每 5 分钟整理一次，这意味着它已经停了 30 天）就会被删掉。为此，项目 M 每次整理时都会检查：收件箱中只要有超过 7 天仍未整理的行（不在 `processed_sources` 中），就在设置页和首页报警。再加上 6.7 的心跳提醒，这种情况在被删除之前早已暴露。如果长期没有新的消费，旧行会多留一段时间，但没有消费时也就不会产生新行，表格不会变大。去重依靠账本中永久保存的凭据，不依赖这些原始行。

### 4.4 去重键与规则

| 情况 | 键／判定 | 结果 |
| --- | --- | --- |
| 同一封邮件被处理两次 | `gmail:msg:<id>` 已存在 | 跳过（PRD 6.2、验收“重复收据”） |
| 同一平台同一订单再次收到收据类邮件 | `order:<platform>:<order_ref>:receipt` 已存在 | 不新增；金额不同 → 原账目标“待核对金额”；金额相同 → 视为重复，不做任何改动（PRD 6.3） |
| 同一次快捷指令触发被重复发送 | `applepay:evt:<event_id>` 已存在 | 跳过 |
| 被删除的自动记录 | 凭据仍在 `processed_sources` | 跳过，不会重新出现 |
| 不同渠道疑似同一笔 | 金额相同且非空 + 时间相差 ≤ 24 小时 + 商家相近（规范化后一方包含另一方，或任一方商家为空）+ 渠道不同 + 未在 `dup_dismissed` 中 | 两笔都标“待核对重复”，共享 `dup_group`，**不合并、不删除**（PRD 6.2） |
| 同一渠道、同一订单、同金额、1 天内的两封不同退款邮件 | 同上，作用于退款 | 标“待核对重复” |
| **DoorDash 收据缺少订单标识** | 同平台、同一餐厅的归一化键相同，且 6 小时内已有未删除收据账目；只有在缺少 `order_ref` 时适用 | 新旧两笔照常入账并标“待核对重复”，共享 `dup_group`。餐厅名从收据主题提取，只保存不可逆哈希；没有餐厅名则不标。Uber 打车不使用此规则（D7） |

“商家规范化”：Unicode NFKC 规范化后转小写，只保留 Unicode 字母和数字。DoorDash 的餐厅键从主题中的餐厅名称计算，账目只保存不可逆哈希，不保存餐厅名称。跨渠道别名包含内置商家名和用户加入名单时设置的显示名／网域。

**邮件账单与 Apple Pay 的跨渠道重复：** 如果你在 App 内用 Apple Pay 付款，而钱包自动化也被触发，就可能出现一笔 Apple Pay 和一笔邮件账单。金额相同、24 小时内、商家相近（含用户配置的别名）时，两笔都会被标为“待核对重复”。需要说明的限制：
- 交易触发器的官方说明是“当我**刷**某张卡时”触发 [S21]，**App 内付款是否会触发【未核实】**（scope 中提到，之前一次 DoorDash App 内付款的测试没有证明能触发）；
- 如果钱包端金额与收据实付总额不同（例如小费后来调整），规则不会标为重复，两笔都会计入；这种情况需要你在核对时留意（风险 R17）；
- Apple Pay 端显示的商家名称【未核实】，别名清单需在实验 A1 或 A2 中按实际显示补充。

### 4.5 软删除与 30 天清理

- 删除：写入 `deleted_at`，并更新 `month_meta`。所有统计和列表都排除 `deleted_at` 不为空的账目（PRD 第 4 节）。
- 恢复：清空 `deleted_at`。由于 `occurred_at` 没变，账目回到原月份并重新计入统计（验收“删除与恢复”）。
- 清理：每天凌晨（费城时间）运行一次，彻底删除 `deleted_at` 早于 30 天前的行。`processed_sources` 不删。
- 被退款关联的原账目被删除时，退款本身仍是独立账目，照常计入（月报按实际存在的账目计算）。

### 4.6 费城时区的月份归属

- 服务器端：`Utilities.formatDate(date, 'America/New_York', 'yyyy-MM')`；在本地测试中使用标准的 `Intl.DateTimeFormat(..., {timeZone: 'America/New_York'})`。两者都使用 IANA 时区数据，会自动处理夏令时。
- **手动录入的时间按“费城时间”理解**：日期选择器显示和提交的都是费城当地时间，服务器把它换算为 UTC。手机在别的时区时也不会改变月份归属（验收“月份归属”：费城 1 月 31 日 23:30 → 1 月）。夏令时回拨时，重复的那一小时取较早的时刻。
- 快捷指令发送带时区偏移的 ISO 时间（例如 `2026-01-31T23:30:00-05:00`），服务器换算为 UTC 后再算月份。
- Gmail 收据使用邮件的 `internalDate`（Gmail 收到邮件的时间）作为 `occurred_at`。**注意：** 这是收据到达时间，不是下单时间；跨月临界情况（例如 1 月 31 日 23:58 下单、2 月 1 日 00:02 收到收据）会归入 2 月。如果收据正文能可靠地提取到下单时间，则改用下单时间 **【收据格式未核实】**。
- 退款按退款邮件的到达时间归月（PRD 6.3）。

## 5. Apple Pay 实体店路线

### 5.1 数据怎样到达账本

1. iPhone「快捷指令」→ 自动化 → 触发条件 **Transaction（交易）**：“When I tap”选择要监听的卡 [S21]。设置为不询问、直接运行（交易触发属于可以自动运行的类型 [S22]）。
2. 快捷指令的动作：
   - 生成一次性 `event_id`（例如用“随机数”动作生成 1 至 999,999,999 之间的数，再与当前时间拼接）。只在本次运行开始时生成一次，失败重试时沿用同一个。
   - 用「获取 URL 内容」动作发送 POST，正文为 JSON [S23]：

     ```json
     {
       "token": "<口令>",
       "event_id": "<一次性编号>",
       "amount_text": "<快捷指令输入中的金额>",
       "merchant_text": "<快捷指令输入中的商家>",
       "occurred_at_text": "<当前日期，ISO 8601 格式>",
       "shortcut_version": "1"
     }
     ```

   - 如果请求失败：显示通知“记账未发送，请手动记一笔”。
3. 收件项目 I 的 `doPost`：检查正文大小（> 4 KB 拒绝）→ 解析 JSON → 用固定时间比较方式核对口令 → 检查字段长度 → 追加一行到 `inbox` → 返回 `{"ok":true}`。口令错误时返回同样简短的错误，不写入任何东西，也不记录正文内容。
4. 主项目 M 整理收件箱：每次定时任务运行时、每次打开记账网页时都会执行。对每一行：
   - 若 `applepay:evt:<event_id>` 已处理 → 跳过。
   - 解析金额：从 `amount_text` 中提取美元金额（接受 `$12.34`、`12.34`、`US$12.34`、带千位分隔符的写法）。解析失败或金额 ≤ 0 → 金额为空，状态“待补全”。
   - 商家为空 → 商家显示为 `Apple Pay`。
   - 新建账目：支出、类别“未分类”、`channel=apple_pay`（PRD 6.1），再做第 4.4 节的跨渠道重复检查。
5. 网页刷新后即可看到。正常情况下，打开网页的那一刻收件箱就会被整理；即使不打开网页，最长 5 分钟后也会被定时任务整理。

> 关于跳转：谷歌脚本网页处理 POST 后，会让客户端跳转到另一个地址取回响应。快捷指令是否跟随跳转、能否显示 `ok` 都**【未核实】**。但 `doPost` 在跳转之前已经执行完毕，所以判断成功的标准是“账本里出现了这笔账”，而不是快捷指令里显示了什么。

### 5.2 实际能拿到哪些字段

- Apple 官方文档只说明交易触发器可以按“刷了哪张卡”触发 [S21]，**没有列出快捷指令输入中包含哪些字段**。
- 社区普遍提到的字段有：金额（Amount）、商家（Merchant）、卡片／通行证名称（Card or Pass）、名称（Name）。**【全部未核实】**
- 可能的问题 **【未核实】**：金额可能是带货币符号的文字；部分银行卡或部分商户可能拿不到金额；交通卡刷卡也可能触发；小费类交易（如餐厅事后加小费）只能拿到刷卡时的金额。
- 设计原则（PRD 6.1）：拿不到金额也照样写入账目，并标为“待补全”。

### 5.3 收件口的保护

**先说清楚剩余风险：**

1. **拿到“网址 + 口令”的人可以伪造支出。** 这样的人可以发送任意数量、任意金额的假交易，项目 M 会把它们自动变成 Apple Pay 支出。这会污染月报总额，还可能让你的真实账目因为“金额相同、时间接近”被标成“待核对重复”。口令是唯一的防线。
2. **即使没有口令，匿名请求也会消耗你的资源。** 每个请求都以你的身份运行，占用你账号“同时运行 30 个”的上限 [S1]。大量请求可能让项目 M 的定时任务和记账网页一时无法运行（报“同时运行的脚本过多”）。不会产生费用，但会影响使用。

| 风险 | 措施 |
| --- | --- |
| 他人只知道网址、不知道口令 | 口令错误时不写入、不读取，立即返回；处理代码极短，尽量缩短占用时间 |
| 口令泄露后被灌入假交易 | ① **限流**：项目 I 用 `LockService.getScriptLock().tryLock(2000)` 获取脚本锁，最多等 2 秒 [S17]；拿不到就返回 `{"ok":false,"reason":"busy"}`，不写入，也不长时间占用执行名额。拿到锁后，一次读取「收件箱」最后 60 行，只统计 `row_type = txn` 的交易行：数出 `received_at` 在最近 1 小时内的行数 `n1`，以及最近 24 小时内的行数 `n24`。若 `n1 ≥ 10` 或 `n24 ≥ 30`，本次拒绝写入（即每小时第 11 笔、每天第 31 笔被拒；正常消费远低于此，数值实施时可调）。为什么读 60 行就够：在上限有效时，任意 24 小时内最多有 30 条交易行和 24 条限流标记行（每小时最多一条），共 54 行 < 60，所以标记行不会挤占统计窗口。**`received_at` 一律是项目 I 在 `doPost` 执行时取的服务器时间**，绝不使用请求中的 `occurred_at_text`，因此伪造交易时间也绕不过限流。这种计数不使用 `CacheService` 或 `PropertiesService`：不会被缓存清除影响，也不占用 Properties 每天 50,000 次读写的共享额度 [S1]，而且只统计口令正确、真正写入的行。**“忙”的情况：** 快捷指令收到 `busy` 时，3 秒后用同一个 `event_id` 重试一次（去重保证不会多记）；仍失败时显示“记账未发送，请手动记一笔”。正常使用时，几乎不会同时有两笔付款，所以基本不会遇到“忙”。快捷指令能否读到返回值同样【未核实】（5.1）；如果读不到，这笔请求就可能没有任何提示，这是接受的风险，记录在 R8。② **方便批量清理**：所有 Apple Pay 账目都有 `channel=apple_pay` 和来源收件行的 `received_at`；“最近删除”旁提供“按渠道和时间段筛选 → 批量删除”。③ 换新口令、归档旧部署、新建部署（换网址），并更新快捷指令 |
| **超限时被拒的真实消费** | **不会悄悄丢掉。** ① 收件口返回 `{"ok":false,"reason":"rate_limited"}`，快捷指令据此显示通知“记账未保存（超出上限），请手动记一笔”（快捷指令能否读到这个返回值受 5.1 的跳转问题影响 **【未核实】**，所以还有下一条兜底）；② 项目 I 在「收件箱」写入一条**限流标记行**（`row_type=rate_limited`，只记录时间和被拒次数，不含交易内容；每小时最多一条，被拒次数累加在这一行上），这样被拒的请求本身不会撑大表格；③ 项目 M 读取标记后，在设置页和首页显示红色警告，并通过小助手发出“Apple Pay 收件口在 X 时拒收了 N 笔，请对照付款记录手动补记”（7A.3）。之后同一标记行的被拒次数如果继续增加，就更新这条消息中的 N，并把它重新设为未读（红点再次出现），所以打开小助手时看到的总是最新的被拒笔数。被拒交易的内容不保存，因为保存它们会让限流失去意义（**需你确认，见 D13**） |
| 快捷指令被分享出去 | **绝不要用 iCloud 链接分享这个快捷指令，也不要截图其中的“获取 URL 内容”步骤**：它里面写着网址和口令。仓库中的 `docs/shortcut-setup.md` 只提供不含口令的图文步骤 |
| 资源被占满 | 不会扣费；记账网页暂时打不开时稍后重试；持续发生时归档部署（收件口立即失效），并手动记账 |
| 恶意内容写入表格 | 所有文本截断到 200 字符；写入前，以 `= + - @` 开头的文本前加单引号，防止被表格当作公式执行 |
| 仓库泄露 | 网址和口令都不进入代码和仓库；仓库中只放 `INGEST_TOKEN` 这个属性名 |

## 6. Gmail 邮件账单路线（DoorDash、Uber Eats、Uber 打车与商家名单）

### 6.1 授权方式与申请的权限

主项目 M 在配置文件中**显式列出**全部权限（不依赖自动检测）[S6]：

| 权限 | 用途 | 敏感级别 |
| --- | --- | --- |
| `https://www.googleapis.com/auth/gmail.readonly` | 只读搜索内置平台及收据候选邮件；技术上可读取整个邮箱，程序按规则筛选（不能发信、不能删信、不能改标签） | 受限（restricted）[S10] |
| `https://www.googleapis.com/auth/spreadsheets` | 读写账本、读取收件箱表格 | 敏感 **【级别未在本次核实】** |
| `https://www.googleapis.com/auth/script.scriptapp` | 创建、删除自己的定时器 | **【未核实其敏感级别】** |

**为什么不用 `GmailApp`：** 官方文档为 `GmailApp.search` 列出的权限是 `https://mail.google.com/`，并注明“或相关 REST API 的适当权限”[S7]。它能否只凭只读权限运行，文档没有写清 **【未核实】**。`https://mail.google.com/` 可以“读取、撰写、发送、永久删除你的所有邮件”，官方建议仅在需要永久删除时才申请 [S10]。为避免这种不确定性，代码中不使用 `GmailApp`，只使用高级 Gmail 服务（对 Gmail API 的直接调用），并在配置文件中只声明只读权限 [S8][S9]。

**对 Gmail 权限范围的诚实说明：** `gmail.readonly` 让程序**有能力读取整个邮箱**，而不只是收据邮件。程序只搜索内置平台及符合条件的名单外收据候选，这是代码层面的自我约束，不是 Google 给的权限边界。名单外邮件不会自动入账。如果想要更窄的权限，只有 `gmail.metadata`，但它看不到正文 [S10]，读不出金额，所以无法使用。

**对表格权限范围的诚实说明：** 项目 M 的 `spreadsheets` 权限让程序**有能力读写你 Google 账号里的每一张表格**，不只是「账本」和「收件箱」。程序只通过脚本属性中保存的两个表格 ID 打开这两张表，这同样是代码层面的自我约束。更窄的组合是 `spreadsheets.currentonly`（只碰绑定的「账本」）加 `spreadsheets.readonly`（只读所有表格，用于读取「收件箱」）。这种组合在网页和定时任务环境中能否成立 **【未核实】**，已列入切片 0b 的通过标准；能成立就改用窄权限，并告诉你。注意：窄权限下项目 M 不能删除收件箱的旧行，所以收件箱清理改由项目 I 负责（4.3）。

**会看到“未验证应用”提示：** 官方表格写明：Gmail 账号发布的谷歌脚本被任何 Gmail 账号使用时，都会走“未验证应用”授权流程，脚注注明“包括发布者本人”[S12]。所以你自己授权时也会看到这个提示，需要点“高级 → 继续”。未验证应用最多 100 个新用户 [S13]，对单人使用没有影响。

**不需要处理刷新令牌：** 授权由谷歌脚本在 Google 内部管理，代码中拿不到、也不保存令牌。这避免了方案 B 中“Testing 状态刷新令牌 7 天过期”的问题 [S14]。

**快捷指令收件口（项目 I）** 只申请 `https://www.googleapis.com/auth/spreadsheets.currentonly`（只能访问绑定的那一张表格）。**【`currentonly` 在匿名网页部署环境中是否可用，需在切片 3 实测】** 如果不可用，可选做法都需要**你来决定（D6）**，不会自动改为大权限：
- (a) 项目 I 改用 `spreadsheets`：这个对外公开的项目将有能力读写你所有的表格，一旦代码有漏洞，影响面最大，**不推荐**；
- (b) Apple Pay 收件口改用方案 B 的 Supabase Edge Function：只有这一部分改用 Supabase，项目 M 定时向 Supabase 取件。这会引入第二个服务，并带来闲置暂停问题（1.2）；
- (c) 暂缓 Apple Pay 自动入账，先交付 Gmail 路线和手动记账，并如实记录 Apple Pay 未达标。

（不采用“由项目 I 再公开一个取件接口”的做法，因为那会多出一个对外公开、可以读出数据的入口。）

### 6.2 怎样撤销授权

1. 立即停止：打开 Google 账号的“已关联应用”页面 `https://myaccount.google.com/linkedapps`，找到项目 M → 移除访问权限 [S19]。之后定时任务会因“需要授权”而失败 [S6]，Gmail 读取立即停止。
2. 彻底停止：在脚本编辑器中删除定时器、归档或删除部署。
3. 停止 Apple Pay 收件口：归档项目 I 的部署，并在 iPhone 上关闭该自动化。
4. 账本数据仍留在你的 Google Drive 中，可以继续查看或删除。

### 6.4 怎样达到“邮件到达后约 15 分钟内入账”

- 定时器：每 5 分钟运行一次 `pollReceipts()` [S5]。
- 每次运行：
  1. 获取脚本锁 [S17]（拿不到就跳过本轮，下一轮再处理）；
  2. **一次合并搜索**：加上 `newer_than:3d`，同时搜索名单平台发件域名和 Gmail「购物」分类或收据类主题词；排除名单外已静音商家。调用 `Gmail.Users.Messages.list('me', {q, maxResults: 50, pageToken})`，按 `nextPageToken` 翻页，受单轮读取上限和运行时限约束，未处理编号留给下一轮。已处理邮件由 `processed_sources` 去重；
  3. 对每个未处理的编号调用 `Gmail.Users.Messages.get(..., {format: 'full'})`，交给 6.5 的共用流程处理；
  4. 按平台更新 `channel_status`（DoorDash、Uber Eats、Uber），包括“邮件到达 → 入账”的耗时，供实验核对。
- **为什么合并搜索，而不是每个平台各搜一次：** 合并后每轮只需一次列表调用。程序从合并结果中排除内置平台、名单商家和静音商家，再读取名单外的收据候选邮件。静音域名在调用 `Messages.get` 前排除。结果按页读取，并受每轮读取上限和运行时限约束；没有处理完的邮件留给下一轮继续。
- 预计耗时：5 分钟的轮询间隔 + 定时器误差 **【未核实】** + Gmail 收件到可搜索的延迟 **【未核实】** + 几秒处理时间。常规情况约 5–10 分钟。内置平台及名单商家共用同一个定时任务，时效相同。
- **Gmail 接口用量重算（对应 1.1 的计费门槛 [S11]）：**
  - 列表：288 次 × 5 单位 = 1,440 单位/天（3 天窗口内平台邮件少于 50 封时只有一页；超过 50 封时每多一页再加 5 单位）。
  - 读取：每封新邮件只读一次，20 单位。因为扫描会包含名单外的收据候选邮件，读取数量以 G1 实测和每轮上限为准；G1 日志只显示日期、网域、识别金额和原因代码，不显示邮件内容。
  - 旧估计约为 2,000–2,500 单位/天；由于现在还会读取名单外的收据候选邮件，不能继续把旧估计当作实际用量。当前每日总量待 G1 实测后更新；计费门槛为 8,000 万单位/天 [S11]。
  - 出错情况：如果程序出错，每轮都把 3 天窗口内的全部邮件（假设 150 封、3 页）重新读一遍：288 × (3 × 5 + 150 × 20) ≈ 87 万单位/天，约为门槛的 1.1%。仍远低于门槛，但状态页会因为“读取次数异常”报警（每轮读取超过 30 封即记录 `READ_VOLUME_HIGH`）。
  - 每轮读取有上限，超过上限的候选邮件留到后续轮询，避免一次读取过多邮件或超出运行时限。
- 每日 90 分钟运行额度：288 次/天，平均每次需 < 18.75 秒 [S1]。扩展扫描后的邮件读取量与单次耗时尚未实测；G1 记录实际读取量。如果实测接近运行额度，改为每 10 分钟一次（D5）。
- 为什么不用 Gmail “推送通知”：推送需要 Google Cloud Pub/Sub 和标准 Cloud 项目，可能涉及结算账户 **【未核实】**。为满足“不可能扣费”的约束，第一版不用推送。

### 6.5 平台规则注册表与共用处理流程

**设计目标（PRD 6.1“以后可以按同样方式添加平台”）：** 每个平台只是一组规则（一个文件 + 一组合成测试样本），去重、退款、修订、D7、跨渠道重复、状态显示等全部在共用流程中处理。以后新增内置平台时，只需新增一个规则文件，在注册表中登记，补上测试样本，再做一次 G1/G2，不用改动共用流程。

**每个平台规则文件提供的内容（纯函数，可在 Node 中测试）：**

| 字段／函数 | 作用 |
| --- | --- |
| `id`、`displayName` | 例如 `doordash` / `DoorDash`、`uber` / `Uber`、`ubereats` / `Uber Eats`。`displayName` 写入账目的“商家” |
| `enabled`、`support_status` | `unverified`（未验证）/ `supported`（已支持）/ `partial`（部分支持：能识别但金额需手动补）/ `unsupported`（未支持），见 6.8 与 D15 |
| `gmailQuery` | 该平台的搜索条件片段（6.4 合并使用） |
| `matchMessage(fromHeader, subject)` | Uber 与 Uber Eats 共用域名时按邮件头识别品牌；Uber 打车记入“交通”，Uber Eats 记入“餐饮”。正文页脚不参与品牌判断 |
| `classify(subject, text)` | 返回 `receipt`（收据）/ `refund`（退款）/ `other`（其他，忽略）/ `uncertain`（看起来有金额，但无法确定类型） |
| `extractTotal(text)` | 返回 `{cents, reason}`；找不到、出现多个不同候选或币种不是美元 → `cents = null` 并给出原因代码 |
| `extractRefund(text)` | 退款金额，规则同上 |
| `extractOrderRef(text, links)` | 订单标识；没有就返回空 |
| `extractOrderTime(text)` + `bodyTimeZone` | 可选。只有能可靠提取下单时间，且已知正文时间所用时区时才使用（D2）；否则使用邮件到达时间（`internalDate`，与时区无关的绝对时间） |
| `merchantAliases` | 用于跨渠道重复判断的内置商家别名；用户加入名单的商家使用显示名称和网域 |
| `category` | DoorDash、Uber Eats 为“餐饮”；Uber 打车为“交通”（PRD 6.1） |

**共用处理流程（每封新邮件）：**

1. 解码正文：HTML → 纯文本，并做 **Unicode NFKC 规范化**，把全角数字、全角冒号、全角美元符号等转成半角，再合并空白、按行切分。
2. 根据发件域名和邮件头确定内置平台。Uber 与 Uber Eats 共用 `uber.com`，分类时以发件人显示名和主题为依据，正文页脚不用于判定商家。会员、钱包及促销邮件为 `other`；其他无法判定的邮件进入 D16 待查看流程。
3. `classify`：
   - `other` → 记录凭据 `ignored_not_receipt`；
   - `uncertain` 或名单外收据候选 → 保存到 `gmail_pending`，不自动入账（D16）；网域、日期和识别金额可见，正文和主题不保存；
   - `receipt` / `refund` → 进入第 4 步。
4. 提取金额、订单标识、时间。
5. 名单内平台邮件交给共用的 `applyReceiptEvent({platform, kind, cents, orderRef, occurredAt, messageId})`。它负责：
   - 去重键 `gmail:msg:<id>`、`order:<platform>:<order_ref>:receipt`（键中加入平台名，不同平台的订单号即使相同也不会冲突）；
   - 6.6 的退款与修订规则；
   - D7：DoorDash 缺少订单号时，仅在同一餐厅且 6 小时内标记；同一封邮件仍按 message id 去重；
   - 4.4 的跨渠道疑似重复（使用平台的 `merchantAliases`）；
   - 写入账目：`channel = gmail_receipt`，`platform = <id>`，商家 = 平台显示名，类别依平台决定（DoorDash／Uber Eats 为“餐饮”，Uber 为“交通”）。
6. 更新该平台状态，运行小助手规则（7A.3）。

**用户管理的邮件商家：** `mail_senders` 保存 `domain`、`display_name`、`category_id`、`mode`（`auto` 或 `muted`）及创建时间。内置平台不写入这张表。用户新增 `auto` 商家后，只有主题像收据且正文恰好找到一个实付总额时才自动入账；金额缺失或主题不像收据时仍进待查看。选择“以后自动记”会加入商家并记录当前这封邮件；选择“不再提醒”会静音整个网域。

**待查看邮件的四个操作（D16）：**

- **记这一笔：** 打开现有记账面板并预填识别到的金额和商家；保存后账目写入 `source_key = gmail:msg:<id>`、`channel = gmail_receipt`，对应待查看行标记已处理。
- **以后自动记：** 用户选择类别后新增或更新该网域的 `auto` 商家规则，并将当前邮件记入账本。
- **不再提醒这个商家：** 新增或更新该网域的 `muted` 规则，并隐藏该网域所有待查看邮件。
- **已查看：** 只关闭当前邮件的待查看状态。

所有新 `api_*` 操作经过现有锁和服务规则包装。`gmail_pending` 缺少网域的旧行仍能显示；未运行新版本 `setupLedger` 前缺少 `mail_senders` 时网页仍可打开。

- 只接受规则声明的“总额标签”，并明确排除 `Subtotal`、`小计` 等“小计标签”。用户自建商家使用通用 Total 类标签。

| 情况 | 处理 |
| --- | --- |

## 7. 月报计算规则（PRD 第 5 节）

### 7.1 通用规则

对月份 M（费城时间），只统计 `deleted_at` 为空且 `month_ny = M` 的账目。

- **待补全（金额为空）**：不计入任何金额，也不计入百分比的分母。`pending_count` = 当月金额为空的账目数（不分支出或收入）。大于 0 时，月报顶部提示“有 N 笔金额未补全，以下统计不完整”。
- **待核对重复、待核对金额**：金额已知，**照常计入**。你处理之前，重复的两笔都会计入，可能高估支出（**需你确认，见第 11 节 D1**）。首页提示条会显示“M 笔待核对”。
- 所有求和都用整数美分。

### 7.2 支出报表

- `支出总额` = 当月支出账目 `amount_cents` 之和（退款为负数，自然扣除）。
- `类别金额` = 按类别求和（退款计入原类别，所以“在类别内抵扣”）。
- `百分比` = 类别金额 ÷ 支出总额 × 100，四舍五入（0.5 进位）保留一位小数。用整数运算计算，例如 `round(类别美分 × 1000 ÷ 总额美分) ÷ 10`，避免浮点误差。所以合计可能显示为 99.9% 或 100.1%（PRD 5.1）。
- 排序：按类别金额从大到小。只显示当月有账目的类别。
- 边界情况：支出总额 ≤ 0（例如当月只有退款）时，不显示百分比，只显示金额；某个类别净额为负时，单独列在最后，并标“净退款”。

### 7.3 收入报表

- `收入总额` = 当月收入账目之和。
- 各收入类别：金额及其占收入总额的百分比。
- 展开某个类别：按 `income_source_id` 分组，空值显示为“未指定来源”。每个来源显示金额及**占总收入**的百分比（PRD 5.2）。
- 不重复相加：总额只从账目直接求和一次；来源只是同一批账目的细分，不参与总额计算。

### 7.4 收支对比

- 两根柱子使用相同刻度（以两者中较大的值为满格），并显示 `差额 = 收入总额 − 支出总额`。差额为负时用醒目颜色。

### 7.5 “上月报表”与更新时间

- 打开月报页时，默认月份 = 当前费城时间的**上一个月**；也可以切换到本月。
- 显示“生成于 {M+1} 月 1 日，最后更新于 {month_meta.last_changed_at}”。报表每次都实时计算，所以补账后会立即更新，不需要保存月报快照。

### 7.6 用 PRD 验收数字核对（这些将直接写成自动测试）

| 场景 | 计算 |
| --- | --- |
| 支出构成 | 12000 + 8000 = 20000 美分；餐饮 12000×1000/20000 = 600 → 60.0%；购物 40.0% |
| 收入来源 | 60000 + 40000 = 100000；兼职 100.0%；A 60.0%，B 40.0% |
| 收支对比 | 100000 − 20000 = 80000 → 差额 800.00 |
| 待补全 | 加一笔空金额支出：总额仍为 20000，`pending_count` = 1 |
| 补填 | 补填为 5000 → 总额 25000，`pending_count` = 0；若该笔属于“日用”：餐饮 48.0%、购物 32.0%、日用 20.0% |
| 退款 | 1 月餐饮 +12000；2 月餐饮 −2000（`refund_of` 指向 1 月那笔）→ 1 月餐饮 120.00，2 月餐饮净额减少 20.00 |

## 7A. 预算与小助手（PRD 6A，2026-10-13 新增）

> 白话版：在设置页填一个“每月总预算”，也可以给部分类别单独设预算；每个月自动沿用，改了只影响当月及以后。每个页面左上角有一个小助手图标，有新提醒时显示小红点；点开是聊天窗口，小助手把提醒和夸奖一条条列出来，下面有几个问题按钮，点一下就回答。小助手**完全按固定规则计算**，不调用任何外部 AI，账目不离开你的 Google 账号，也没有打字框。

### 7A.1 数据模型（「账本」表格新增工作表）

**`budgets`（预算历史，只追加或更新当月行，从不改动过去月份）**

| 列 | 说明 |
| --- | --- |
| `id` | 文本 |
| `scope` | `total`（总预算）或某个支出类别的 `category_id` |
| `amount_cents` | 正整数；**空 = 从该月起取消此预算** |
| `effective_from` | `YYYY-MM`，从哪个月起生效 |
| `updated_at` | UTC ISO |

- **某月某范围的预算** = 该范围 `effective_from ≤ 该月` 的行中，`effective_from` 最大的那一行；它的金额为空或没有这样的行 → 该月没有此预算。
- **修改**只能在设置页针对“当前月”（费城时间）进行：如果该范围已有 `effective_from = 当月` 的行，就更新这一行；否则追加一行 `effective_from = 当月`。因此：
  - 下个月不用重填，查找时会自动沿用最近的一行（PRD 6A.1“每月自动沿用”）；
  - 过去月份查到的仍是它们当时的那一行，数字不变（验收“预算沿用”）。
- **校验**：金额必须 > 0；`scope` 只能是 `total` 或**未归档的支出类别**；**“未分类”不能设预算**，服务器端拒绝，界面中也不显示该选项。为了不依赖类别名称，`categories` 增加 `system_key` 列，“未分类”的值为 `uncategorized`。这一类别被 Apple Pay 默认使用，所以设为不可删除、不可改名（**需你确认，见 D9**）。
- 某类别被归档时，从当月起自动写入一行“空金额”，即取消该类别预算；过去月份不受影响。**取消归档后，预算保持取消状态**，不会自动恢复；设置页中该类别的预算为空，需要你重新填写。
- 类别预算之和可以高于总预算，此时设置页显示一条提示，但不阻止保存（**D10**）。

**`assistant_messages`（小助手发出的提醒和夸奖）**

| 列 | 说明 |
| --- | --- |
| `id`、`created_at` | |

| `value` | 例如 `none` / `near` / `over`，或待处理笔数 |
| `updated_at` | |

### 7A.2 计算规则

以下都只统计**未删除的支出账目**（`type=expense`、`deleted_at` 为空），金额用整数美分，时间一律按费城时区。

| 名称 | 定义 |
| --- | --- |
| 已用（某月、某范围） | 该月 `month_ny` 内、该范围（总预算 = 所有支出类别，**包括“未分类”**；类别预算 = 该类别）已知金额之和。**退款为负数，自然冲减已用**（PRD 6A.1）。退款按退款日期归月，所以 2 月收到 1 月订单的退款，冲减的是 2 月的已用 |
| 待补全笔数（某范围） | 同范围内金额为空的笔数。大于 0 时，附注“有 N 笔未补全，预算统计不完整”（PRD 6A.1）。待补全不算作 0，也不计入已用 |
| 剩余 / 超出 | `预算 − 已用`；为负时显示“超出 X 美元” |
| 已用比例 | `已用 ÷ 预算`，用整数运算四舍五入到整数百分比显示；判断阈值时直接比较 `已用 × 100 ≥ 阈值 × 预算`，避免四舍五入造成误判 |
| 今天 | 费城时间的当天日期 `d`；本月天数 `L`（28–31，按实际月份） |
| 时间进度 | `d ÷ L`（今天算作已过去） |
| 本月到今天（按钮 1） | `month_ny = 本月` 且 `date_ny ≤ 今天` 的账目。**日期在今天之后的账目（例如提前录入的 16 日后账目）不计入**（验收“本月到今天”）。输出支出总额、收入总额、差额、支出各类别、收入各类别，以及这一范围内的待补全笔数 |
| 上月同期（按钮 4） | 本月 1 日至今天（第 `d` 天）对比上月 1 日至第 `min(d, 上月天数)` 天。例：3 月 30 日对比 2 月 1–28 日（闰年为 1–29 日），并注明“上月只有 28 天，已与上月全月比较”；2 月 28 日对比 1 月 1–28 日。只比较支出总额，并显示差额和变化百分比（上月同期为 0 时不显示百分比）。两边的待补全笔数都会注明 |
| 哪个类别花得最多（按钮 3） | 本月（截至今天）支出净额最大的类别；并列时都列出；本月没有支出时回答“本月还没有支出记录” |
| 还能花多少（按钮 2） | 本月有效的总预算和各类别预算的剩余或超出金额；没设预算时提示去设置页设置 |
| 待补全／待核对（按钮 5） | 本月及以前所有未删除账目中，待补全、待核对重复、待核对金额的笔数；附带 `goto:pending` 动作（行为见 7A.1 `action`；按月分布由 `attentionMonths` 计算，规则与本计数相同，各月之和等于总数） |
| 月报预算小结（PRD 6A.5） | 所选月份 M 使用**M 当月有效的预算**（过去月份显示当时的预算），列出总预算与各类别预算的已用、剩余或超出金额；外加一句总结，由与小助手相同的规则模块生成（例如“本月总预算剩余 120 美元，餐饮超出 15 美元”）。M 没有任何预算时不显示这一块 |

### 7A.3 提醒与夸奖规则（PRD 6A.3 的默认值）

| 规则（`skill_id`） | 触发条件 | 去重键 / 何时再次出现 |
| --- | --- | --- |
| 接近预算 `budget_near` | 当月某范围的已用比例 ≥ `budget_near_pct`（默认 80%）且 ≤ 100% | 状态键 `budget:<月>:<范围>` 从 `none` 变为 `near` 时发一条。之后即使继续增加也不重复；如果因为退款、删除或预算调高回到 `none`，再次升到 `near` 时会再发 |
| 超出预算 `budget_over` | 已用 > 预算 | 同一状态键变为 `over` 时发一条（从 `none` 直接跳到 `over` 只发“超出”这一条）。**从 `over` 回落到 `near`（例如收到退款）不发消息**，只把状态更新为 `near`；之后再次超出时，会再发一条“超出” |
| 进度良好 `good_progress` | 设置了总预算、`d > L ÷ 2`（月中以后）、已用比例 ≤ 时间进度 − `good_progress_margin_pts` 个百分点（默认 15，D8），并且本月没有待补全 | 每月最多一次，键 `good_progress:<月>` |
| 上月表扬 `last_month_praise` | 进入新月份后第一次运行规则时，若上月有总预算且上月已用 ≤ 上月预算 | 每月最多一次，键 `last_month_praise:<上月>`。上月有待补全时，话里注明“还有 N 笔未补全，结论可能变化”（D12） |
| 待处理 `pending_items` | 待补全 + 待核对笔数 + D16“待查看邮件”数 > 0 | 使用两个**跨日保存**的状态键：`pending:last_sent_count`（上次发送时的笔数）和 `pending:last_sent_date`（上次发送的费城日期）。当前笔数 > `last_sent_count`，并且 `last_sent_date` ≠ 今天时才发；发送后同时更新这两个键。笔数归零时，`last_sent_count` 重置为 0 |
| Apple Pay 被限流 `apple_pay_rate_limited` | 收件箱中出现新的“限流”标记行（见 5.3） | 每个标记行最多一次，键 `rate_limited:<标记行时间>` |

**规则什么时候运行：** 每次写入账目（手动保存、删除、恢复、补填）、每次自动入账（Gmail 处理、收件箱整理）以及每次打开网页时，在脚本锁内运行一次 `runAssistantRules(now)`。规则只读取账本数据和 `assistant_state`，写入新消息和新状态。**同样的输入重复运行，不会产生第二条消息**（幂等）。

**红点与已读：** 每次加载页面和每次写入后，服务器返回 `unread_count`；大于 0 时，左上角图标显示小红点。打开对话窗口时，调用 `markAssistantRead()` 把所有未读消息的 `read_at` 设为现在，红点随即消失（验收“预算提醒”）。

### 7A.4 为以后扩展和升级预留的接口边界

小助手拆成三层，界面只认“消息”，不认规则：

```
账本数据 ──> buildSnapshot(now)            # 纯函数：只含按月、按类别的汇总、预算、待处理笔数、日期信息；
                                           # 不含商家、备注、邮件等原始内容
           ──> 技能（skills）注册表         # 每个技能：{ id, kind: 'reminder' | 'question', label?,
                                           #             evaluate(snapshot, state) -> { messages[], newState } }
           ──> 消息 Message                 # { id, skill_id, text, items?: [{label, amount_cents}], action? }
界面：只负责显示消息列表和 kind='question' 技能的按钮
```

- **加一个按钮或一种提醒**：新增一个技能文件并注册，界面和存储都不用改（PRD 6A.2“预留位置”）。
- **问题按钮的回答是即时计算的**，不存入 `assistant_messages`，因此不会产生红点；只有提醒类技能的消息才会保存。
- **以后升级为真正的 AI 对话**：可以新增一个“回答者”，遵守同样的约定，即输入为 `snapshot`（加上用户输入的文字），输出为 `Message[]`；界面再增加输入框。**本方案不设计这一部分。** 接入外部 AI 会涉及费用、把账目汇总发送到 Google 以外的服务，以及开放自由输入，必须**另行获得你的批准**（PRD 6A.2）。`snapshot` 只含汇总数据，就是为了以后把可能外传的数据范围降到最小。

## 8. 网页结构与状态提示（概要）

- 单页应用：`doGet` 返回 HTML，包含 viewport 设置以适配手机。底部导航：账目／记一笔／月报／设置（PRD 第 1 节）。

## 8A. 界面语言切换（PRD 6B，2026-10-26）

- **做法：翻译“显示出来的文字”，不改业务代码。** 新增 `ui/i18n.js.html`（在 `ui/app.js` 之前引入），内含英文对照表。英文模式下，用 `MutationObserver` 监听页面变化，把文字节点以及 `aria-label`、`placeholder`、`title` 属性翻译成英文；`confirm()` 的提示也经过同一个翻译函数。中文模式下不做任何处理，现有中文界面与测试完全不变。
- **对照表的两种条目：** ① 整句对照（去掉首尾空白后完全相同才替换，保留原有首尾空白）；② 带数字的模板：先把金额（如 `$1,234.56`）、百分比、日期、整数替换成占位符 `{0}`、`{1}`…，再查模板；少数含用户内容的句子用显式正则。查不到的文字保持原样，并记入 `window.__i18nMissing`，供测试找出漏翻的地方。
- **切回中文：** 每个被翻译的节点在 `WeakMap` 里记住原文，切回中文时逐个还原，再重新渲染当前页面，所以不需要刷新网页。
- **默认类别：** 内置类别按编号对应英文名（如 `exp_dining → Dining`），由服务器在 `api_bootstrap` 的类别清单中附带 `name_en`；前端据此把这些类别名加入对照表。自建类别没有 `name_en`，保持原样。表格中的类别名不变。
- **服务器生成的文字**（错误提示、小猫助手消息、状态说明）仍以中文生成和保存，显示时由同一对照表翻译；旧消息只要符合模板也会显示为英文。
- **交易表格导出：** `api_generateTransactionReport(startDate, endDate, lang)` 新增可选参数 `lang`（`'en'` 或省略为中文），表头、月份标题、说明文字和默认类别名按该语言写入新文件；不影响账本。
- **语言记录位置：** 浏览器 `localStorage('ledger.lang')`，值为 `zh` 或 `en`，读写失败时按中文处理。同时更新 `<html lang>` 和页面标题。
- **已知限制：** 用户输入的内容如果和对照表里的词完全相同（例如备注只写了“退款”），英文模式下也会显示成英文；表格里保存的内容不受影响。
- **测试：** 在模拟浏览器中切到 English，依次打开各页面、子页面和小猫助手，断言页面中除用户输入的内容外不含中文；切回中文后与原界面一致；导出在 `lang='en'` 时表头为英文。
